# CodeQuest

Космическая корпорация, которой управляет ваш код на JavaScript. Каждое задание —
практическая задачка по сюжету: пока функция не написана, механика не работает и
раздел интерфейса не открыт. Ванильные HTML, CSS и JavaScript, без сборщика и
внешних библиотек.

## Демо

**https://kovalenkoserhii2107-maker.github.io/CodeQuest/**

## Как это устроено

Главный принцип: **интерфейс ничего не считает сам**. Разделы корпорации просят
выполнить функцию, которую вы написали в задании, и показывают её результат.
Сломали решение — раздел честно покажет ошибку вместо данных.

Каждое задание проходится в два шага:

1. **Теория** — пишете функцию в редакторе, пока не пройдут тесты.
2. **Практика** — вызываете свою функцию в **консоли корпорации** с настоящими
   значениями. Результат попадает в базу корпорации: вводите своё имя — и в
   реестре появляется именно ваш командир. Только после этого задание считается
   закрытым и открывается раздел интерфейса.

Прогрессия строго линейная: следующее задание открывается только после полностью
закрытого предыдущего, а вместе с ним появляется новый пункт меню.

| № | Задание | Чему учит | Что открывает |
| --- | --- | --- | --- |
| 1 | Личное дело командира | объект, поля, сокращённая запись | Командный центр |
| 2 | Космоверфь | методы в объекте, `this`, `find` | Верфь |
| 3 | Склад корпорации | методы, состояние объекта, валидация | Склад |
| 4 | Биржа труда | копии объектов, спред, условия | Экипаж |
| 5 | Сборка корабля | `reduce`, агрегация | Корабль |
| 6 | Предстартовая диагностика | `some`, массив проблем | Диагностика |
| 7 | Сводка по базе | `reduce`, поиск максимума | База данных |
| 8 | Своя панель на дашборде | функция как виджет | Панели |
| 9 | Полётный план | арифметика, `Math.ceil` | Маршруты |
| 10 | План с грузом | доработка своей функции, значение по умолчанию | — (улучшает `planFlight`) |
| 11 | Аварийный резерв | доработка: новые поля в ответе | — (улучшает `planFlight`) |
| 12 | Первая экспедиция | цикл с накоплением и `break` | Экспедиция |
| 13 | Ревизия топлива | поиск ошибки в готовом коде | Ревизия |
| 14 | Торговля рудой | сортировка, распределение по лимитам | Рынок |
| 15 | Боевая сводка | `filter`, `map`, агрегация по типу | Арсенал |
| 16 | Обмен ударами | ограничение значений, `Math.max` | Полигон |
| 17 | Боевой вылет | цикл `while` и состояние боя | Бой |

### Одна функция, несколько этапов

Функция пишется не один раз. `planFlight` появляется в задании 9 простой —
расход по массе корабля, — а дальше её дорабатывает сам игрок: задание 10
учитывает груз, задание 11 добавляет аварийный резерв. Это отдельные задания
со своим условием, но код тот же самый.

Как это устроено:

- **Редактор открывается вашим кодом прошлого этапа**, а не пустой заготовкой:
  доработка начинается с того, что уже работает.
- **Блок «что изменилось»** над редактором называет три вещи: что уже работает,
  что меняется в условии, что нужно дописать.
- **Прежние проверки прогоняются заново** и помечаются как «прежнее поведение».
  Доработка вправе добавить в ответ новые поля, но старые значения меняться не
  должны: на функцию уже опираются разделы интерфейса и соседние функции.
- **Прежняя версия никуда не девается.** Кнопки под блоком показывают построчное
  сравнение с предыдущим этапом и возвращают старый код в редактор.
- **Приложение работает на последнем пройденном этапе.** Разделы не помнят, каким
  заданием была написана функция: `appSource()` собирает по одной активной версии
  на каждое имя, поэтому два объявления `planFlight` встретиться не могут.

Черновик в редакторе живёт отдельно от рабочей версии: сломанный код, который не
прошёл тесты, в приложение не попадает и разделы не гасит.

### Моё приложение

Раздел «Моё приложение» — это витрина написанного: по карточке на каждую функцию,
с её этапами, ссылкой «Мой код» на задание, где эта версия написана, и ссылкой
«Где работает» на раздел, который считает ею. Здесь же видно, что добавит текущее
задание. Раздел открыт с самого начала и заполняется по мере прохождения.

### Ревизия топлива

Каждая заправка и каждый рейс оставляют запись в журнале топлива
(`state.fuelLog`): вид операции, объём, пояснение и время. Остаток бака нигде не
дублируется — его сводят, пройдя журнал от начала до конца.

Это делает задание 13, и оно устроено иначе: в редакторе не пустая заготовка, а
готовая функция с ошибкой. Её нужно прочитать, понять, почему приход и расход
считаются одинаково, и починить. Раздел «Ревизия» показывает, сошёлся ли
результат вашей `fuelBalance` с настоящим баком.

### Экономика: топливо, руда и деньги

С девятого задания у корпорации появляется оборот. Топливо покупается на
космопорте по 40 ¢ за тонну и хранится в баке (600 т). Расход считает ваша
функция `planFlight`: сначала по массе корабля, а после доработок — по массе
с грузом и с аварийным резервом. Чем больше модулей вы навесили, тем дороже
рейс, и тяжёлый корабль может не дотянуть до дальнего пояса даже с полным
баком. Заправка спрашивает у плана `total`, если он там появился, и `fuel`,
пока его нет: доработка функции сразу меняет поведение корпорации.

Экспедицию проводит ваша `runExpedition`: час за часом буры грызут породу,
пока не кончится время или не забьётся трюм (150 т). Привезённая руда
ложится в бункер (300 т), а продаёт её ваша `sellOre` — покупатели дают
разную цену и берут разный объём, так что выручка зависит от того, как вы
распределите груз.

Это первый источник дохода: до него кредиты приходили только за задания.

### Война: орудия, щиты и премии

С пятнадцатого задания верфь продаёт боевые модули: лазер, рельсотрон и два
щита. Атаку и защиту корабля считает ваша `combatStats` — она отбирает из
стоящих на корабле модулей только боевые и складывает по типам. Прочность корпуса берётся от
массы: тяжёлый корабль дольше держится под огнём.

Урон считает ваша `strike`: щит вычитается из залпа, но единица проходит
всегда, поэтому безнадёжных мишеней не бывает — бывают долгие. Проверить
расчёт можно на полигоне, где мишени не отвечают.

Весь бой ведёт ваша `runBattle` — цикл `while` с лимитом в 20 раундов,
иначе два неуязвимых корабля зависли бы навсегда. За победу штаб платит
премию: от 12 000 ¢ за дрон до 95 000 ¢ за крейсер. С одним лазером
крейсер не взять — сначала придётся заработать на рельсотрон.

### Консоль корпорации

Консоль открывается после первых пройденных тестов. В ней доступны все функции,
которые вы уже написали, и объект `corp` с реальными данными компании:

```
› createCommander("Сергей Коваленко")
{ name: "Сергей Коваленко", rank: "Командир", experience: 0, credits: 0 }
✓ Личное дело «Сергей Коваленко» занесено в реестр корпорации

› createShipyard("Орион", corp.catalog)
› createWarehouse(1000)
› hireCrewMember(corp.commander, corp.candidates[0])
› assembleShip("Квест", corp.modules)
› checkReadiness(corp.ship, corp.crew)
```

Поля `corp`: `credits`, `commander`, `catalog`, `modules` (стоят на корабле),
`stock` (лежат на складе), `stockUsed`, `crew`, `candidates` (биржа), `ship`,
`battleShip`, `warehouseCapacity`, `fuel`, `ore`, `fuelLog`, `offers`,
`threats`, `targets`, `report`.

В области видимости — рабочие версии всех ваших функций, поэтому одна может
вызвать другую: `runExpedition(corp.expeditionShip, planFlight(corp.ship, 240))`.

### Бортовая база данных

Всё, что создаёт ваш код, складывается в базу — коллекции записей, которые видно
в отдельном разделе и из которых можно читать:

```
› db.insert("logs", { text: "первый рейс" })
› db.all("ships")
› db.last("commanders")
› db.find("crew", member => member.role === "Капитан")
› db.count("reports")
```

Код выполняется в воркере, поэтому работает с копией базы: чтение отвечает
сразу, а записи копятся списком операций и применяются к настоящей базе уже в
основном потоке — как в обычном клиенте базы данных. Консоль показывает, что
изменилось: «База данных: записей добавлено: 1».

### Склад и корабль — разные места

Купленный модуль приезжает на склад и там лежит: массы кораблю он не даёт,
энергии не потребляет, в сборку не идёт. Чтобы он заработал, его ставят на
корабль в разделе «Склад». Установленный модуль склад больше не занимает.

Обратный путь тоже есть: снять с корабля на склад (если там осталось место)
и сдать верфи за полцены. Так исправляют неудачную закупку.

В коде это два списка: `state.inventory` — склад, `state.fitted` — корабль.
Все расчёты корабля — масса, энергобаланс, боевая сводка, добыча — идут по
установленным. В консоли `corp.modules` — тоже они, а `corp.stock` — то, что
лежит на складе.

### Энергобаланс и как его выправить

Покупка на верфи смотрит только на деньги и место — энергобаланс её не
волнует, а предстартовая диагностика лишь сообщает о проблеме, ничего не
запрещая. Поэтому корабль легко собрать с отрицательным энергобалансом.

Зато он бьёт по делу. Часть энергии уходит на тягу — тонна массы стоит
единицы мощности на каждые 50 тонн, и без двигателя тяга не потребляет
ничего. Если выработки не хватает, питание делится между потребителями
поровну, и КПД равен отношению выработки к общему расходу.
Все модули работают на эту долю: буры добывают меньше тонн в час, орудия
бьют слабее, щит держит хуже. Корабль с шестью модулями и балансом −150
работает на 44%: бур выдаёт 1 т/ч вместо 3, атака падает со 135 до 60.

Выправляют баланс двумя способами: снять потребителя или поставить реактор
помощнее. В каталоге два реактора — «Искра-М» (+120, 150 т) и «Искра-Т»
(+300, 260 т). Второй обычный реактор проблему не решает: шесть модулей
дают −150, с двумя «Искрами-М» получается 990 т и всё ещё −30, а третья
уже не помещается. Заменой на «Искру-Т» выходит 950 т и +30.

`check-economy` следит, что каталог остаётся сбалансированным: корабль,
забитый потребителями под завязку, обязан поддаваться выводу в плюс.

Чтобы это не было приговором, модуль можно снять со склада: верфь выкупает
его за 60% цены, место освобождается, деньги возвращаются. Без демонтажа
склад удавалось забить потребителями так, что реактор уже не помещался, —
и выхода из этого положения не было.

Карточки каталога заранее показывают, каким станет склад и энергобаланс
после покупки, так что до кассы видно, во что обойдётся лишняя пушка.

### Карточки в реестре стареют

Практика записывает в базу карточку — снимок на тот момент. Купили модуль,
пересобрали корабль — и снимок устарел.

Поэтому задания, чья практика только записывает карточку и ничего не тратит
(командир, верфь, склад, сборка, диагностика), помечены `practice.refresh`:
их функцию можно вызвать в консоли заново, и запись обновится. Награда
второй раз не начисляется — обновляется только карточка.

```
› assembleShip("Квест", corp.modules)
Запись в реестре обновлена: Корабль «Квест» собран: 3 модулей, 430 т, энергобаланс +20
```

А `corp.ship` в консоли вообще не берётся из базы: он пересчитывается вашей
же функцией `assembleShip` по тому, что сейчас на складе, — ровно как это
делает раздел «Корабль». Консоль и интерфейс обязаны показывать одно и то же.

### Свои панели

Панель — это ваша функция: она читает базу и возвращает описание того, что
показать. Регистрация сохраняет исходник, и панель запускается заново при каждой
отрисовке — на Командном центре и в разделе «Панели».

```js
function shipPanel(db) {
  const ship = db.last("ships");
  if (!ship) return { title: "Корабль", value: "не собран" };
  return { title: "Корабль", value: ship.mass, unit: "т", note: `Энергобаланс ${ship.energy}` };
}
```

```
› dashboard.add("ship", shipPanel)
```

Описание панели: `title`, `value`, `unit`, `note`, а также `rows` (массив пар
«подпись — значение») и `list` (список строк). Снять панель — `dashboard.remove("ship")`
или кнопкой в разделе «Панели».

### Панель рисует график

Добавьте в описание поле `type` — и вместо числа появится график. Данные берите
из базы: тогда картинка пересчитывается сама, как только записи меняются.

| `type` | Что рисует | Поля |
| --- | --- | --- |
| `gauge` | круговая шкала | `value`, `max`, `label`, `unit` |
| `fill` | полоса заполненности | `value`, `max`, `label`, `unit`, `tone` |
| `balance` | шкала с нулём посередине | `value`, `max`, `label` |
| `bar` | столбики | `items: [{ label, value }]`, `unit` |
| `spark` | линия по точкам | `points: [числа]` |

```js
dashboard.add("ore", db => ({
  title: "Руда по маршрутам",
  type: "bar",
  items: db.all("routes").map(route => ({ label: route.to, value: route.ore })),
  unit: "т",
}));
```

`tone: "progress"` меняет смысл цвета: полная полоса становится зелёной, а не
тревожной — это для прогресса, а не для запасов. Нечисловые значения графики
отбрасывают, поэтому кривые данные портят картинку, но не ломают страницу.

Команда выполняется в воркере с таймаутом, история листается стрелками ↑ и ↓ и
переживает перезагрузку. Результат проверяется: `createShipyard("Орион", [])`
практику не закроет — консоль объяснит, что каталог не передан.

Что это значит на практике:

- каталог на Верфи рисует **ваш** `getCatalog()`, а кнопка «Купить» ищет модуль
  **вашим** `findModule(id)`;
- занятое место на Складе считает **ваш** `usedSpace()`;
- найм проходит через **вашу** `hireCrewMember()` — она решает, хватает ли денег,
  и симулятор списывает ровно ту сумму, которую посчитал ваш код;
- массу и энергобаланс корабля выдаёт **ваш** `assembleShip()`;
- допуск к вылету определяет **ваш** `checkReadiness()`.

## Как запустить

Модули ES и Web Worker не работают по протоколу `file://`, поэтому нужен любой
локальный сервер:

```bash
python3 -m http.server 8000
# затем откройте http://localhost:8000/
```

## Редактор

Редактор написан с нуля: подсветка синтаксиса, номера строк, парные скобки,
умные отступы (`Enter` раскрывает блок), `Tab` и `Shift+Tab` для отступов,
`Ctrl + /` для комментария, `Ctrl + Enter` для запуска тестов.

Автодополнение вызывается точкой после переменной или по `Ctrl + Space`: рядом со
списком открывается окно справочника с сигнатурой, описанием, подводными камнями
и примером. Окно можно перетащить за заголовок и растянуть за любую сторону или
угол — положение и размер запоминаются.

Код выполняется в Web Worker с таймаутом 3 секунды, поэтому бесконечный цикл не
вешает вкладку.

## Как устроено задание

Каждое задание — это не только условие и тесты, но и учебная часть.

- **Сигнатура** — что за функцию писать и что она должна вернуть. Видна сразу под сюжетом.
- **Условие** разбито на пункты: что приходит на вход, какие поля вернуть, что считать краевым случаем.
- **Разбор темы** — короткий урок под заданием: приём объясняется своими словами и показывается
  рабочим примером с комментариями. Это для того, кто видит тему впервые.
- **Что понадобится** — напоминание в четыре строки для того, кто тему уже знает.
- **Подсказки** открываются по одной и идут ступеньками: сначала направление, потом приём,
  потом почти решение. Дословных строк из эталона в них нет — за готовым кодом есть
  отдельная кнопка с половинной наградой.

Отчёт о прогоне тестов показывает вызов, полученное значение и ожидаемое в одном формате,
а под ними — блок «что не так»: различия названы по именам полей, вроде «нет поля credits»
или «crew: ждали элементов: 1, получили 0». Искать разницу глазами в двух длинных строках
JSON не нужно.

## Как добавить задание

Допишите объект в массив `QUESTS` (`js/data/quests.js`):

```js
{
  id: 'mining',
  order: 7,                                   // следующий номер цепочки
  title: 'Добыча руды',
  topic: 'Циклы и накопление',
  difficulty: 3,
  reward: { credits: 30000, xp: 150 },
  unlocks: { view: 'mining', label: 'Добыча' },  // какой раздел откроется
  story: 'Зачем это корпорации.',
  brief: 'Что должна делать функция.',
  practice: {                                  // практическая часть в консоли
    title: 'Запустите добычу',
    hint: 'Что и зачем вызвать в консоли.',
    example: 'mineOre(corp.modules)',
    validate: value => (typeof value === 'number' ? true : 'Команда должна вернуть число'),
    commit: (value, api) => {
      api.setRecord('ore', value);
      return `Добыто ${value} т руды`;
    },
  },
  theory: ['Подсказка по теории'],
  fn: 'mineOre',
  starter: 'function mineOre(field) {\n}\n',
  hints: ['Первая подсказка'],
  solution: 'function mineOre(field) {\n  return 0;\n}\n',
  tests: [
    { name: 'Обычный случай', args: [[1, 2]], expected: 3 },
    { name: 'С методами', expr: 'return mineOre([]).length;', expected: 0 },
  ],
}
```

Затем добавьте в `index.html` раздел `id="view-mining"` и пункт меню
`data-view-item="mining"` (скрытый по умолчанию), а в `js/ui.js` — функцию
отрисовки, которая берёт данные через `runPlayerCode('mining', '…')`.
`node tests/check-quests.mjs` проверит, что всё связано.

## Как добавить этап доработки

Этап — обычное задание, которое продолжает уже написанную функцию. Раздел он не
открывает (`unlocks` не нужен), зато указывает предшественника:

```js
{
  id: 'mining-depth',
  order: 8,
  fn: 'mineOre',              // то же имя функции, что и у прошлого этапа
  extends: 'mining',          // задание, чей код дорабатывается
  inheritTests: true,         // прежние проверки прогоняются заново
  changes: {
    works: 'Функция уже считает добычу по числу буров.',
    changed: 'Теперь у жилы есть глубина: чем глубже, тем медленнее бур.',
    todo: 'Учтите поле depth и оставьте прежние поля ответа на месте.',
  },
  practice: { refresh: true, /* … */ },   // повторная практика не платит дважды
  // starter не нужен: редактор откроется кодом прошлого этапа
  tests: [ /* только новые проверки */ ],
}
```

Правила, которые проверяет `node tests/check-quests.mjs`:

- предшественник существует, идёт раньше по `order` и пишет ту же функцию;
- заполнены `changes.works` и `changes.todo` — иначе непонятно, что дорабатывать;
- решение прошлого этапа **не проходит** новые проверки: если проходит, доработки
  на самом деле нет;
- решение нового этапа проходит и новые проверки, и все унаследованные.
